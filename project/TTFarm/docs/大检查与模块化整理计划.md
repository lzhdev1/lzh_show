# TTFarm 大检查与模块化整理计划

日期：2026-11-24  
状态：只读审计已完成，代码未改动，等待确认后执行

## 一、结论先行

TTFarm 目前已经形成了 `game`（纯规则）、`scene`（Three.js 场景）、`ui`（React 面板）三层，源码没有循环依赖，`pnpm typecheck` 与 `pnpm build` 均通过。数据目录也完整：94 种作物（24 普通 + 20 野菜 + 50 草药）、50 种鱼、100 种菌、20 种动物、291 条图鉴。

但这次审计发现了需要优先处理的问题：

1. **肉品没有进入云端存档链路**：`GameData` 有 `meat`，但 `pickSave`、`RemoteState`、服务端 `FarmSave`、`farm_states` 表都没有它；换设备会丢肉，切换账号还可能看到上一个账号留在本地 store 里的肉。
2. **好友/大厅停车场的场景资源没有完整释放**：`hallParking` 加入 scene 后，`game.dispose()` 只移除了 `salesHall`，没有释放 `hallParking`，热更新或重复启动会留下 GPU 资源。
3. **存档合并按数组下标匹配地块**：服务端 JSONB 或人工修库一旦改变地块顺序，冲突合并会把两块地的状态错配。
4. **发言气泡与未读记录存在内存/时钟问题**：`seen`、`arrivals` 无上限增长；气泡用服务端时间与本地 `Date.now()` 直接比较，客户端时钟偏差超过 30 秒时新消息不再冒泡。
5. **本地草稿解析没有统一兜底**：`localStorage` 草稿损坏时，`signIn`/`checkpoint`/`upload` 里的 `JSON.parse` 可能直接把登录打断。
6. **存在明确的死代码和仓库垃圾**：`FishingGearPanel.tsx` 没有任何引用；`docs` 里 4 张未被 README 引用的截图（约 1.5 MB）；README 的目录说明已过时。
7. **服务端与客户端各写一套存档初始化/服装白名单**：`initialSave` 与 `initialData`、`COUTURE_IDS` 与 `couture.ts`、装饰样式与 `decor.ts` 都在两处维护，肉品字段的遗漏就是这种漂移的结果。

这些问题里，第 1、2、3 条建议作为 P0 先修；第 4、5 条作为 P1；结构性拆分放在 P0/P1 稳定之后，避免“大搬家”掩盖功能回归。

## 三、审计发现清单

### P0：先修，影响数据或资源

#### P0-1 肉品存档断链

证据：

- `src/game/state.ts` 的 `GameData` 含 `meat`，`initialData()` 初始化 `meat: {}`，牧场出栏 `butcherAnimal` 会写入 `meat`。
- `account.ts` 的 `pickSave()` 没有 `meat`；`applyRemoteState()` 也不写 `meat`。
- `src/api/client.ts` 的 `RemoteState` 没有 `meat`。
- `blog_front/src/lib/ttfarm-save.ts` 的 `FarmSave`、`normalizeSave`、`loadSave`、`saveState` 没有 `meat`。
- `project/TTFarm/db/schema.sql` 的 `farm_states` 没有 `meat` 列。

影响：

- 换设备/清缓存后肉品消失；
- 同一浏览器切换账号时，`meat` 可能继续留在全局 `ttfarm-save-v1` store 中，形成跨账号数据串台；
- 肉品只能在本机“看起来存在”，与云端存档不一致。

修复方向：新增 `farm_states.meat JSONB`，把 `meat` 接入 `FarmSave`、`RemoteState`、`pickSave`、`applyRemoteState`、`initialSave`、`normalizeSave`、`loadSave`、`saveState`；旧账号默认 `{}`，`save_version` 升到 9；同时写迁移脚本和“A 账号肉品不进入 B 账号”的回归用例。

#### P0-2 地块合并按数组下标匹配

证据：`src/game/saveMerge.ts` 用 `local.plots[i]`、`remote.plots[i]` 逐项比较；`RemoteState` 是 JSONB 数组，服务端虽然会重排，但旧数据、手工修库或未来接口改动都可能改变顺序。

影响：顺序一变，可能把 A 地块的作物/浇水次数合并到 B 地块，造成存档错乱或误判冲突。

修复方向：建立 `Map<plotId, PlotState>`，先校验两端的 id 集合、数量、重复 id，再按 id 合并；顺序只在最终输出时统一排序。补充“远端地块倒序/缺项/重复项”的单元测试。

#### P0-3 大厅停车场资源未释放

证据：`runtime/loop.ts` 把 `hallParking` 加进 `view.scene`；`dispose()` 只对 `salesHall` 遍历释放，`hallParking` 没有对应的 remove/dispose；`world.dispose()` 只清理 `world.group`，不包含 `hallParking`。

影响：HMR、重复 `startGame` 或测试多次启动时，几何体、材质、纹理留在 GPU；移动端长时间开发/热更新可能表现为显存上涨。

修复方向：抽出统一的 `disposeObject3D(root)`，对 `salesHall`、`hallParking` 等直接挂在 scene 上的节点统一释放；`renderer.dispose()` 后补充 `forceContextLoss()`（仅在确认 WebGL 上下文回收行为后启用），并加资源数量回归检查。

### P1：稳定性和可维护性

#### P1-1 发言记录无上限，气泡受时钟偏差影响

证据：`src/game/chat.ts` 的 `seen` 是 `Set`，`arrivals` 是 `Map`，房间切换只 `seen.clear()`，没有按消息数量/时间裁剪；`remember()` 用 `Math.abs(Date.now() - message.at) > BUBBLE_MS` 判断，服务端与本地时钟偏差大时会把正常新消息当成旧历史。

修复方向：`seen`/`arrivals` 改为有上限的 LRU 或按消息 id 保留最近 `KEEP` 条；气泡改用“消息首次到达本地的时间”作为起点，首次历史拉取只做基线；补时钟偏移 ±5 分钟的测试。

#### P1-2 草稿 JSON 解析缺少兜底

证据：`account.ts` 的 `signIn`、`checkpoint`、`upload`、`refresh` 多处直接 `JSON.parse`；`readDraft` 只处理 `localStorage` 读写异常，不处理内容损坏。

影响：本地草稿被截断/写坏后，登录或自动保存会抛异常，用户可能卡在登录页或持续报错。

修复方向：统一 `parseDraft()`，校验对象形状、字段类型和版本；损坏时把原文备份到 `-corrupt-backup` 并回退到服务端存档，不阻塞登录。

#### P1-3 远端快照和本地持久化校验不完整

证据：`applyRemoteState` 直接使用 `state.plots`、`state.seeds`、`state.harvest`；`useGame.persist.merge` 对 `saved.harvest`、`saved.seeds` 只做对象展开，没有过滤未知 key、负数、`NaN`；`coins/xp` 也没有统一兜底。

影响：脏 JSON、旧客户端字段或人工修库可能让金币变成 `NaN`、库存出现未知物品、图鉴出现无效 key。

修复方向：把 `normalizeSave`/`normalizeLocalState` 变成唯一入口；所有数值走 `finiteInt(value, min, max, fallback)`；所有记录走白名单；在 `applyRemoteState` 和 `persist.merge` 两侧都调用同一套归一化。

#### P1-4 死代码与文档垃圾

已确认：

- `src/ui/FishingGearPanel.tsx` 没有任何引用，是上一轮商店改版后遗留的独立面板。
- `FISH_TOTAL`、`rodAutoEquip`、`MUSHROOM_PHASE_MS`、`MUSHROOM_MUTATION_BLURB`、`TOWN`、`attachRiverFish`、`disposeClayMaterials`、`createMushroomGlow`、`MushroomModel`、`backHeight`、`WaterIcon` 在 `src` 内没有引用；其中 `buildShape`/`paintAnimal` 仍被 `scripts/bake-ranch-animals.mjs` 使用，属于工具链 API，不能按“死代码”直接删。
- `docs/bubble-check.png`、`docs/demo-首屏.png`、`docs/demo-主站入口.png`、`docs/demo-作品卡.png` 未被 README 引用，属于过程截图。
- `README.md` 的目录结构还写着“4 张角色头像、4 张贴图”，与当前 `public` 的 58 个资源不符。

修复方向：删除确认无引用的 UI 组件和纯死导出；把工具链专用导出标注 `@tooling` 或移到 `scripts` 侧；过程截图先归档到 `D:\DouBao\DBCache\ttfarm-docs-archive`，再从仓库删除；README 重写目录与模块说明。

### P2：结构性整理

#### P2-1 UI 面板状态是一组布尔量

`App.tsx` 用 10 个布尔值管理 `shop/profile/farm/ranch/ranking/friends/codex/market/carStore/backpack`，每次新增面板都要改四五处。建议改为 `activePanel: "shop" | "profile" | ... | null`，用一个 `openPanel`/`closePanel` 管理，Escape、遮罩、互斥打开只保留一份逻辑。

#### P2-2 状态仓库与主循环职责过重

`game/state.ts` 同时承担数据初始值、作物动作、商店、背包、鱼竿、图鉴、牧场/野外的组合；`runtime/loop.ts` 同时承担输入、访客切换、驾驶、钓鱼、城镇交互、相机、同步、资源释放。建议按“行为切片”拆分，保持 `state.ts` 作为对外 facade，避免一次性改所有 import：

- `game/store/cropSlice.ts`：买种、播种、浇水、收获、扩建；
- `game/store/shopSlice.ts`：种子/鱼竿/加速卡/鱼饵；
- `game/store/backpackSlice.ts`：容量、升级、装备；
- `game/store/fishingSlice.ts`：鱼竿、鱼饵、鱼篓；
- `game/sim/inputController.ts`、`visitController.ts`、`driveController.ts`：从 `loop.ts` 提取；
- `game/saveContract.ts`：`GameData`、`pickSave`、`FarmSave` 的唯一契约，服务端与客户端共用。

#### P2-3 大场景生成器拆分

`scene/world.ts`、`crops3d.ts`、`wildAuras.ts`、`wildGarden.ts` 都在 700–961 行，属于场景生成器，改动风险高于纯逻辑。建议放到 P2 的第二轮，按“地形/河流/植被/氛围/作物几何”拆，不做视觉重做。

#### P2-4 服务端共享规则

当前 Dockerfile 只把 11 个 `game` 文件复制到 `blog_front/farm-rules`，服务端 `ttfarm-save.ts` 又手写 `initialSave`、`COUTURE_IDS`、`readDecor`。建议新增 `src/game/saveContract.ts` 并加入 Docker 复制清单，服务端只保留数据库/HTTP 适配，不再复制业务常量。
