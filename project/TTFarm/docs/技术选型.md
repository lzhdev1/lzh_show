# TT农场 · 技术调研与选型

> 版本 v0.1 ｜ 2026-11-06 ｜ 状态：待确认后进入骨架搭建

## 1. 需求与约束

**产品目标**：一款可在浏览器直接玩的 3D 农场经营小游戏，核心循环为「开地 → 买种子 → 播种 → 浇水 → 成熟 → 收获 → 卖菜 → 再投资」。

**硬约束**

| 约束 | 说明 | 对选型的影响 |
|------|------|--------------|
| 要 3D，但不能重 | 拒绝 Unity / Godot WebGL 这类十几 MB 起步的导出包 | 只用渲染库，不用完整游戏引擎 |
| 单容器、子路径部署 | 与 blog-agent、rag-assistant 一致：`lzhshow.top/ttfarm/` 由 nginx 路径分流到独立容器 | 纯静态产物 + nginx 镜像最省事，不引入 Node 运行时 |
| 作品集契约 | 作品卡读 `blog_front/src/lib/projects.ts`，详情页跳 `links.demo`（当前是 `https://lzhshow.top/blog-agent/` 这种子路径） | 必须是「一个可独立部署的 Web 应用」，不能只是页面里的一段组件 |
| 开发机 | RTX 4070 8G / 32G / i7，Windows + Vite 本地热更新 | 不需要本地跑重型构建链，也不做 Blender 重度建模 |
| 单人维护 | 一段时间的业余项目，要能随时停下来继续写 | 拒绝 ECS、状态机框架、复杂依赖注入，逻辑集中在几个纯函数模块 |

**明确不做**：多人联机、账号体系、真实经济、物理引擎、后处理特效链、内置关卡编辑器。

## 2. 候选方案调研

| 方案 | 核心包体积（gzip） | 3D 能力 | 上手成本 | 判断 |
|------|------------------|---------|----------|------|
| **Three.js** | 核心约 168 kB（v0.175，Bundlephobia），按需 tree-shaking 后更小 | WebGL2 渲染全可控，无内置物理/GUI，需要自己写 | 中（API 直白，文档/示例最多） | **推荐** |
| **React Three Fiber**（Three 的 React 封装） | Three 基础上再加 React 协调器，约 220 kB 起 | 同上，组件化组织场景 | 低（熟 React 的话） | 备选：UI 与场景都在 React 里更统一，但逐帧逻辑容易被 React 状态拖慢 |
| **Babylon.js** | 完整包约 1.4 MB（v8.1），ESM tree-shaking 后可到 ~500–700 kB | 内置物理、GUI、阴影、 inspector，功能最全 | 中 | 不推荐：能力远超本项目需要，包体和概念量都偏重 |
| **Babylon Lite**（2026 年新出的精简版） | 官方宣称比 Babylon.js 小约 19 倍（34 kB 量级场景） | 新，生态与文档尚在建设 | 中 | 观望：数据好看，但太新，不适合当作品集的底座 |
| **PixiJS（2.5D 等距）** | 约 40 kB | 纯 2D 渲染引擎，做等距斜视农场靠贴图与图层排序 | 低 | 备选：最轻、最稳，但是「看起来 3D」，不是真 3D |
| Unity / Godot WebGL | 15 MB+ 起 | 强 | 高 | 排除：与「不想太重」直接冲突 |

补充事实（用于判断轻量方案的可行性）：

- R3F 官方文档明确说明逐帧动画应放在 `useFrame` 里用 `lerp/damp` 手写，高频值不要进 React state；也支持 `frameloop="demand"` 按需渲染以省电。
- 性能预算的通用经验值：桌面端单帧 draw call 控制在 200 以内、重复物体超过 10 个用 `InstancedMesh`；本项目地块 + 作物正好落在这个模式里。
- 低模美术素材有成熟 CC0 来源：Quaternius（Farm Buildings / Farm Animal Pack）、KayKit、Kenney，均可商用、免署名。但它们多为 FBX/OBJ，需要 Blender 转 GLB 才能进 Web 管线 —— 这是本条路线的隐形成本。

## 3. 结论：技术选型

| 层次 | 选择 | 理由 |
|------|------|------|
| 语言 | **TypeScript** | 作物表、存档结构、事件参数都需要类型兜底，后期改数值配置不会静默出错 |
| 构建 | **Vite 7**（ESM） | 冷启动快、`base` 支持子路径、产物就是纯静态文件，天然适配 nginx |
| 渲染 | **Three.js（按需 import，不用 examples 全家桶）** | 168 kB 级别，够用且完全可控；不需要引擎的物理/动画系统 |
| 相机 | **PerspectiveCamera 透视 + OrbitControls 自由环绕**（fov 42°，极角 28°–69° 限位，距离 9–34） | 2026-11-08 由正交等距改为透视：等距投影抹掉深度线索，画面偏「平面」；透视让近处围栏大、远处谷仓小，屋顶与树木的体积一眼可读。环绕不设方位限制但极角与距离限位，任何角度都是成立的构图，不会转到地面以下或把农场挤出画面 |
| 状态 | **Zustand + persist** | 1 kB 级，`getState()` 可在渲染循环里直接读，不触发 React 重渲染；`persist` 一行接 localStorage |
| 游戏循环 | 单个 `requestAnimationFrame` + **固定步长逻辑 tick（1s）** | 生长/经济按秒结算，渲染按帧插值；逻辑与渲染彻底分离，逻辑可单测 |
| UI | **DOM 覆盖层**（React + Tailwind 4） | HUD、种子面板、商店、飘字全用 DOM：成本低、可访问性好、不占 draw call；Tailwind 只产 CSS 不产运行时 |
| 交互拾取 | Three 的 `Raycaster` 打地块网格 | 不做物理，不需要碰撞体 |
| 存档 | **localStorage（自动存档 + 手动导出 JSON）** | 单机游戏不需要账号；离线生长用「时间戳差值」推导，天然支持关掉网页继续长 |
| 部署 | 静态产物并入作品集主站 `blog_front/public/ttfarm/`（同域名、同端口、无独立容器） | 详见 §7（2026-11-07 由“独立容器 8120”改为并入主站） |
| 测试 | Vitest（只测 `game/` 纯逻辑） | 经济、成熟判定、离线结算是唯一会「算错钱」的地方 |

**一句话**：*Three.js 负责画，Zustand 负责记，React 只负责面板，Vite 打包成一个静态目录，直接挂进作品集主站。*

**为什么不用 R3F**：这个项目的逐帧对象是「几十个地块 + 作物」，用命令式 Three 写生命周期更短、更可控；React 只接 UI 层，等于拿到 R3F 的开发体验收益，却不承担 React 协调器进渲染循环的风险。

**为什么不上 2.5D PixiJS**：能省 80% 的美术和相机工作量，但作品集里「3D 游戏」这个卖点会打折。既然目标是展示，就保留真 3D。

## 4. 3D 呈现策略（决定性的一步）

### 4.1 美术路线：先程序化，后贴素材

| 阶段 | 做法 | 收益 |
|------|------|------|
| v0.1–v0.3 | **程序化低多边形**：几何体（Box / Cylinder / Cone / Icosahedron）+ 纯色/顶点色材质 + 平面着色（`flatShading`）拼出地块、木屋、水井、栅栏、树、作物 | 零素材、零版权、零加载、零 Blender 环节；风格天然统一；改配色即换皮 |
| v0.4+ | 用 Quaternius / KayKit 的 CC0 包替换关键物件（木屋、动物、成熟作物），Blender 批量导出 GLB | 提升完成度，但只在关键位置替换，不整体换皮 |

这样第一版就能跑起来，不会卡在「找素材 / 学 Blender」上。

### 4.2 场景与地块

- 农场为 **N×M 网格地块**（初始 3×2 = 6 块，可扩建到 6×4 = 24 块），每块地是一个带 `userData.plotId` 的网格，顶点色表示土壤状态（干土 / 湿润 / 已开垦）。
- 作物按 **3–4 个生长阶段**换模型/缩放：种子（土堆小点）→ 幼苗（两片叶）→ 成株（茎叶）→ 成熟（果实 + 轻微上下浮动动画）。
- 静态景物（栅栏、树、石头）在初始化时用 `BufferGeometryUtils.mergeGeometries` 合并成 1–2 个 mesh，把 draw call 压到个位数。
- 光照：1 个 `HemisphereLight` + 1 个 `DirectionalLight`，阴影只开一张 1024 的贴图，且只让建筑与树投影（地块、作物不投影）。

### 4.3 性能预算（目标：集成显卡 60fps）

| 指标 | 预算 |
|------|------|
| JS（含 React） | ≤ 260 kB gzip |
| 美术资源 | ≤ 4 MB（首版程序化时为 0） |
| draw call | ≤ 60（地块/作物用 InstancedMesh 或合批） |
| 三角面 | ≤ 60k |
| 设备像素比 | 上限 2（低端设备降到 1.5） |
| 纹理 | 单张 1024 atlas 或纯色材质 |

## 6. 数据模型（存档契约）

```ts
type CropId = "radish" | "cabbage" | "tomato" | "corn" | "strawberry" | "pumpkin";

interface CropConfig {
  id: CropId;
  name: string;            // "萝卜"
  seedPrice: number;       // 买种子价
  sellPrice: number;       // 单份售价
  yield: number;           // 一次收获产出份数
  growMs: number;          // 成熟所需真实时间（毫秒）
  unlockLevel: number;     // 解锁等级
  stages: number;          // 生长阶段数
}

interface Plot {
  id: number;              // 0..N
  unlocked: boolean;       // 是否已开垦
  crop: CropId | null;
  plantedAt: number | null; // 时间戳（毫秒），离线生长靠它
  wateredAt: number | null; // 最近一次浇水时间
  waterBoost: number;      // 累计浇水加速（0–0.3）
}

interface SaveV1 {
  version: 1;
  coins: number;
  level: number;
  xp: number;
  plots: Plot[];
  inventory: Record<CropId, number>;  // 未卖出的收成
  seeds: Record<CropId, number>;      // 未播的种子
  savedAt: number;
}
```

**离线生长规则**：`成熟 = savedAt + growMs * (1 - waterBoost) <= now`；加载时一次性结算所有地块，成熟则标记为可收获，不模拟逐秒。这样既真实又不耗算力。

## 7. 部署与作品集接入

> **2026-11-07 方案变更**：不再使用独立容器与 8120 端口。作品集主站（Next.js，8100）本身就能托管静态文件，游戏的 Vite 产物直接作为主站的一个子目录发布，**同域名、同端口、零新增服务**。下文的独立容器方案作废，仅保留作历史记录。

**现行方案（静态目录并入主站）**：

1. `pnpm sync-to-site`（= `vite build` + `scripts/sync-to-site.mjs`）把 `dist/` 同步到 `blog_front/public/ttfarm/`；
2. Next.js 的 `public/` 目录会原样托管，`/ttfarm/assets/*`、`/ttfarm/avatars/*` 直接可访问；
3. `public/` 不支持“目录即索引”，所以在 `blog_front/src/proxy.ts`（Next 16 的 proxy 约定）里把 `/ttfarm` 与 `/ttfarm/` 改写到 `/ttfarm/index.html`，并且**不进入 next-intl 的语言路由**；
4. 游戏产物随 `blog_front` 镜像一起发布（`Dockerfile` 的 runner 阶段本来就 `COPY /app/public`），部署流程 `git pull` + `docker compose -f docker-compose.prod.yml up -d --build` 一行不变；
5. Vite `base: '/ttfarm/'` 保证所有资源路径都带子路径前缀，无需 nginx 改写。

**为什么不用独立容器**：游戏没有服务端逻辑（存档在 localStorage），独立容器的唯一价值是“单独发布”，代价却是多一个镜像、多一个端口、多一段 nginx 配置和一条 CI 步骤。作为作品集里的一张作品卡，和主站同生命周期更简单。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 美术素材 FBX→GLB 环节卡住 | 进度停滞 | 首版全程序化，美术替换设为可选项而非前置 |
| 种植/收获的「点击 → 菜单 → 操作」在手机上过重 | 手感差 | UI 用底部抽屉 + 大按钮；一次点击直接弹出该地块可用操作 |
| 真实时间生长被改系统时间刷收益 | 单机作弊 | 单机不处理；未来上云端再用服务端时间 |
| 包体被 Three examples / drei 拖大 | 加载慢 | 只 import 用到的模块，禁止 `import * as THREE from "three/examples/..."` 全家桶 |
| 作品集主站 `/assets` 与游戏资源路径冲突 | 资源 404 | Vite `base: '/ttfarm/'` + nginx 透传前缀（不使用剥离前缀方案） |
